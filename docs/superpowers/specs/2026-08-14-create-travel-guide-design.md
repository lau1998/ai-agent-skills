# 旅游攻略 Skill 设计

## 目标

新增 `create-travel-guide` Skill，用于在充分理解旅行需求后，联网核验动态信息并生成可执行的旅行攻略。Skill 必须先集中收集信息，在理解度达到 95% 且不存在关键缺项后才能开始调研和编排行程。

该 Skill 归入 `other`，因为主要交付物是旅行攻略，不是代码或工程配置。

## 设计原则

- 先理解旅行者，再研究目的地；信息不足时不提前生成攻略。
- 尽量一次性询问全部缺失信息，避免逐题来回追问。
- 复用用户已经提供的信息，不重复提问。
- 把“无偏好”“请你决定”等明确授权视为已理解，而不是缺失信息。
- 动态事实必须联网核验，不能把模型记忆或估算表达为当前事实。
- 路线、时间、预算、体力和安全约束必须相互一致。
- 输出形式服从用户选择，不为了视觉效果牺牲准确性。
- 不代替用户预订、付款或提交个人信息。

## 触发范围

以下需求应触发该 Skill：

- 制定国内、出境、跨城、周末或长途旅行攻略。
- 规划亲子、家庭、情侣、朋友、独自旅行或多人团体行程。
- 规划自驾、公路旅行、公共交通或多种交通组合。
- 优化已有行程的路线、节奏、预算、住宿区域或交通方案。
- 将已确认的旅行方案整理为 Markdown、图文 HTML 或 PDF。

仅查询单个景点营业时间、单段交通、签证政策或酒店价格时，可直接完成事实查询，不强制进入完整攻略流程。代订、代付和提交证件信息不在职责范围内。

## 核心状态与门控

Skill 按以下状态推进：

1. `收集信息`：解析已有信息并生成一次性问题清单。
2. `等待补充`：接收答案，处理冲突和剩余关键缺项。
3. `确认理解`：理解度达到 95% 后，向用户总结已理解的旅行信息。
4. `联网调研`：用户没有纠正摘要时，按准确性规则核验动态事实。
5. `编排行程`：形成可执行的日程、交通、住宿和预算方案。
6. `质量校验`：检查时间、路线、费用、体力、安全和来源完整性。
7. `交付`：按用户选择输出 Markdown、HTML，或在 HTML 获批后导出 PDF。

理解度不足、关键项缺失、答案冲突、网络不可用或关键事实无法核验时，不得越过对应门控。

## 一次性问询

`references/intake.md` 定义完整问询表。执行时先提取对话中已有答案，只询问缺失项，并把问题按下列主题一次性列出：

### 旅行基本信息

- 出发地、目的地和途经地。
- 确切日期或可浮动日期、总天数、可调整范围。
- 旅行目的，例如休闲、亲子、摄影、美食、探亲或商务附带游览。

### 同行人员

- 旅游总人数及成员关系。
- 儿童人数和年龄、老人情况。
- 行动不便、无障碍、孕期或其他照护需求。

### 交通与自驾

- 往返交通和当地主要交通方式。
- 是否自驾、租车、包车或公共交通。
- 自驾时补充车辆类型、驾驶员人数、驾照适用性、单日驾驶时长上限、是否接受环线、山路和夜间驾驶。

### 预算与住宿

- 总预算或人均预算、币种，以及是否包含往返大交通。
- 住宿类型、每晚预算、房间需求、区域偏好。
- 是否接受频繁换酒店。

### 节奏与偏好

- 旅行节奏、通常起床时间、是否安排夜生活。
- 每日步行承受能力、休息频率和最晚结束时间。
- 兴趣、必去项目、可选项目和明确避开的内容。

### 饮食、健康与安全

- 饮食偏好、忌口和过敏。
- 慢性病、药物、海拔、天气或运动限制。
- 对高风险活动、偏远地区和治安风险的接受程度。

### 已有安排与输出

- 已购买的机票、车票、住宿、门票和不可移动的固定时间。
- 需要 Markdown、独立图文 HTML 还是后续 PDF。
- 是否允许使用 AI 生成的封面或氛围示意图。

问询应允许用户用编号快速回答。用户明确表示某项“无偏好”“不需要”或“由你决定”时，记录为已理解或已授权决策，不再追问同一项。

## 理解度计算

`references/intake.md` 使用以下权重计算理解度：

| 信息组 | 权重 |
| --- | ---: |
| 核心旅行事实 | 25% |
| 同行人员与行动能力 | 15% |
| 交通与自驾限制 | 15% |
| 预算与住宿 | 15% |
| 节奏、兴趣与必去项目 | 15% |
| 饮食、健康与安全 | 10% |
| 输出形式与图片授权 | 5% |

每组只按已经明确回答或明确授权 Agent 决定的字段计分。理解度达到 95% 只是必要条件，以下关键项任一缺失时仍必须阻断：

- 目的地。
- 出发地。
- 日期或旅行时长。
- 旅行人数和人员构成。
- 主要交通方式。
- 预算范围。
- 安全或行动能力限制，包括用户明确回答“没有”。

首次回复必须集中询问全部缺失项。后续若仍低于 95%，只追问影响方案的剩余关键问题，不重复完整问卷。答案相互冲突时，先指出冲突并请求确认，不自行选择其中一个答案。

达到门槛后，先输出一份简短的“已理解旅行信息”，包含所有关键事实、授权 Agent 决定的事项和暂定假设。用户纠正后重新计算理解度；用户没有纠正时再进入联网调研。

## 联网调研与准确性

`references/research-verification.md` 定义来源选择、交叉验证和引用记录。

### 来源优先级

1. 政府、使领馆、交通运营方、景点或场馆官网。
2. 官方旅游局、气象、道路和公共安全机构。
3. 可信地图、票务和预订平台，用于路线、班次和价格交叉核验。
4. 当地主流媒体和高质量旅行资料，用于补充体验类建议。
5. 社交媒体只用于发现灵感，不得作为动态事实的唯一证据。

官方来源能够明确回答时，可使用一条权威来源。官方信息缺失、过期或不同来源不一致时，至少使用两个相互独立的来源交叉验证，并在攻略中说明不确定性。

### 必须按旅行日期核验的内容

- 签证、入境、证件、保险和健康要求。
- 天气、季节风险、节假日、罢工或公共安全警示。
- 景点营业时间、临时闭馆、门票、预约和入场限制。
- 航班、铁路、轮渡、公交或自驾路线的可行性。
- 道路封闭、限行、收费、停车、加油或充电条件及驾驶疲劳。
- 高风险活动的年龄、健康、装备和运营限制。
- 对总预算有实质影响的住宿、交通和门票价格。

每项关键动态事实必须记录来源链接和核验日期。价格应标注币种、计价单位、包含内容和查询时点；无法确认的费用只能标注为估算区间，并清楚写明估算依据。

不得将搜索摘要当作最终证据，应尽量打开来源正文核验。不得把模型记忆、未经核验的博客内容或单条社交媒体帖子写成当前事实。

网络不可用时停止最终攻略生成，并说明尚未完成核验。关键事实无法核验时，暂停受影响的方案，列出已验证的替代选项；不得用猜测填补。

## 行程编排与质量校验

`references/itinerary-quality.md` 定义编排规则和交付前检查。

### 按日编排

每日行程至少包含：

- 日期、住宿地和当天主题。
- 按时间顺序排列的活动和建议停留时长。
- 点位之间的交通方式、预计耗时和必要缓冲。
- 用餐建议和休息时段。
- 预约、票务、着装、天气或安全提醒。
- 雨天、闭馆或体力不足时的备用方案。

第一天和最后一天必须结合抵离时间，不安排无法实现的满日行程。跨城或换酒店日要计算退房、行李、候车、交通延误和入住时间。

### 全局一致性

交付前逐项检查：

- 路线是否减少无意义折返，同一区域活动是否合理聚合。
- 开放时间、预约时段和交通班次是否互相兼容。
- 每日活动量是否符合儿童、老人、行动能力和旅行节奏。
- 自驾时长、夜驾、山路、停车、补能和驾驶员休息是否符合用户限制。
- 住宿位置是否支持当日和次日路线。
- 核心费用是否落在预算内，是否保留合理应急余量。
- 必去项目是否全部安排，避免项目是否确实排除。
- 高风险活动、天气和健康条件是否有明确替代方案。

发现路线、时间、预算或体力冲突时，必须重新编排，不得只在备注中提示冲突后仍交付不可执行方案。

## 预算设计

预算按用户指定的总额或人均口径输出，并区分：

- 往返大交通。
- 当地交通或租车相关费用。
- 住宿。
- 餐饮。
- 门票和活动。
- 保险、签证、通信或其他准备费用。
- 应急预留。

每项活动标记为 `免费`、`核心付费` 或 `可选付费`。预算紧张时，优先保留必去项目和安全相关支出，给出可以删除的可选项目，而不是用未经核验的低价压缩预算。

## 输出形式

`references/output-formats.md` 维护不同格式的内容契约。无论形式如何，核心事实必须一致。

### Markdown

默认在对话中提供，适合快速审阅和后续调整。至少包含：

- 已确认的旅行摘要。
- 假设、币种和核验日期。
- 按日行程。
- 住宿区域和交通建议。
- 预算明细。
- 行前准备、天气、安全、礼仪和紧急信息。
- 完整来源列表。

### 图文 HTML

用户选择图文形式时，生成可独立打开、响应式的 HTML。内容与 Markdown 保持一致，图片必须带说明、来源和链接，移动端不得出现文字溢出、遮挡或不可用交互。

### PDF

只在用户明确要求时，从已经审阅通过的 HTML 导出 PDF。PDF 必须经过页面渲染检查，确保分页、图片、链接、表格和中文字体正常。HTML 未获确认或导出失败时，保留可用的 Markdown，不交付损坏的 PDF。

## 图片规则

优先使用官方图片或许可清晰、可复用的真实图片，并保留图片来源、作者或机构、许可信息和原始链接。无法确认图片使用条件时，改用文字和官方页面链接。

使用 AI 图片前必须先询问用户。用户未明确同意时不得生成。用户同意后，AI 图片只可用于封面或氛围示意，不得用于证明酒店实况、道路条件、景点现状、天气或其他事实。

每张 AI 图片必须同时满足：

- 图注明确写出 `AI 生成示意图`。
- HTML `alt` 文本包含 `AI 生成示意图`。
- 来源列表或图片说明再次声明该图片为 AI 生成。

如果找不到可靠图片，宁可省略图片，也不能使用来源不明或容易误导的内容。

## 安全与隐私边界

- 不执行预订、支付、购买、取消或退款。
- 不向第三方提交姓名、证件号、联系方式、银行卡或健康资料。
- 不把攻略视为法律、签证、医疗或安全机构的替代意见。
- 对签证、入境、健康和高风险活动给出官方来源与核验日期。
- 紧急电话、使领馆信息和当地求助渠道必须按目的地核验。
- 用户要求明显危险、违法或违反当地规定的活动时，拒绝该部分并给出合规替代。

## 错误处理

- 信息不足：停留在问询阶段，不进行联网调研或生成成品攻略。
- 答案冲突：列出冲突项并请求确认，不自行推断。
- 理解度低于 95%：只追问剩余关键问题。
- 关键阻断项缺失：即使总分达到 95% 也不进入调研。
- 网络不可用：停止最终攻略生成并告知未核验范围。
- 关键事实不可核验：暂停受影响的计划并提供已核验替代方案。
- 来源互相矛盾：优先官方且日期更新的来源，仍无法判断时保留不确定性。
- 图片来源或许可不可靠：省略图片。
- 未获得 AI 图片授权：不得调用生成工具。
- HTML 或 PDF 生成失败：保留可用的 Markdown，不交付损坏文件。

## 验证方案

实现遵循 Skill 文档的 RED-GREEN-REFACTOR：先记录未加载新 Skill 时的基线行为，再编写 Skill，并用相同场景验证行为改善。至少覆盖以下场景：

1. “帮我做一份日本旅行攻略”会触发一份完整的一次性问卷，而不是直接生成行程。
2. 用户已经提供的目的地、日期和预算不会被重复询问。
3. 缺少同行人数、主要交通方式或预算时，即使其他信息充分也会阻断。
4. 用户回答“住宿由你决定”时，该项计为已理解并记录为授权决策。
5. 自驾请求会收集车辆、驾驶员、驾照、单日时长、环线、山路和夜驾限制。
6. 理解度达到 95% 后先输出理解摘要，再开始联网调研。
7. 营业时间、交通、票价和入境规则等动态事实包含来源链接和核验日期。
8. 路线、时间、预算或体力发生冲突时会重新编排，而不是交付冲突方案。
9. 未获得同意时不生成 AI 图片；获得同意后，图注和 `alt` 都包含 `AI 生成示意图`。
10. Markdown 与 HTML 的日期、路线、价格和来源等核心事实保持一致。
11. 网络不可用或关键来源无法访问时，不会编造动态信息或交付伪完整攻略。
12. 用户只查询单个事实时，不被迫完成整套旅行问卷。

实现完成后还需执行：

- 扫描并清除初始化模板中的所有占位内容。
- 运行官方 `quick_validate.py` 校验 Skill 目录。
- 检查 `agents/openai.yaml` 与 `SKILL.md` 的名称、描述和默认提示一致。
- 检查四个 `references/` 文件都由 `SKILL.md` 直接链接，且不存在更深层依赖。
- 运行项目目录与登记完整性检查。
- 所有行为测试通过后，才把 `create-travel-guide` 唯一登记到 `catalog.yaml`。

## 边界与后续演进

首版不实现实时预订、自动价格监控、地图平台写入、路线导航、账号登录、支付、第三方 API Key 管理或专用生成脚本。

如果真实使用中出现稳定需求，可在后续版本分别评估：

- 确定性的理解度计算和问卷状态脚本。
- 地图路线、距离或海拔的结构化校验。
- HTML 模板和 PDF 导出脚本。
- 经用户授权的价格监控或提醒能力。

这些能力必须保持来源可核验、用户明确授权和平台可替换，不应改变首版“先理解、再核验、后规划”的核心门控。
