# 共享测试分支集成

本项目的 `dev`、`test`、`pre` 等分支是共享测试分支。以仓库 `AGENTS.md` 的最新规定为准。

1. 除非用户在当前任务中明确指定目标分支和操作范围，不直接在共享测试分支上修改、提交、cherry-pick、改写历史或强制推送。用户明确要求直接修改时，执行前说明分支、文件或操作范围，并只做已授权内容。
2. 功能开发、缺陷修复和测试先在功能分支完成、验证并提交。只有用户明确要求 push，才推送功能分支；需要测试环境时，再按用户指定的目标测试分支执行合并。进入测试环境的请求本身不构成 push 授权。
3. 合并前确认当前工作区、暂存区和未跟踪文件均为空，再获取目标测试分支的最新远端状态并核实远端引用。切换到目标分支；本地不存在时，从已核实的远端提交建立同名本地分支。切换后复查清洁状态，比较本地与远端目标提交；本地落后时仅快进同步，领先、分叉或无法核实时停止。同步后确认两者指向同一提交，且工作区和暂存区仍干净。
4. 确认源分支和目标分支，按 [提交前多代理审查](pre-commit-review.md) 审查输入；审查无问题后，再使用 `git merge --no-ff --no-commit` 暂停自动提交。该命令会自动更新暂存区；测试分支只承载本次合并及其冲突解决，不夹带功能分支之外的业务修改。
5. 发生冲突时逐文件核对共同基点、功能分支和测试分支。合并结果须保留功能分支的全部需求与改动，并兼顾目标分支已有行为；不得直接接受任一侧的整文件内容来跳过判断。
6. 完成合并后检查冲突标记及完整差异，运行相关定向测试和静态检查，并按 [提交前多代理审查](pre-commit-review.md) 复审最终合并结果。复审无问题后才人工暂存冲突解决文件并核对最终差异，再创建合并提交；只有用户明确要求推送该合并结果时才推送。若业务语义无法从代码和需求判断，保留现场并说明待决冲突。
