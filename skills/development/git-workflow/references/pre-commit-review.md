# 提交前多代理审查

此门槛适用于每个拟提交的变更，在主动暂存或产生提交前执行。审查旨在发现问题，不能保证代码绝对正确，也不能代替测试。

1. 用 `git status`、`git diff --cached`、`git diff` 和未跟踪文件内容确定拟提交的完整范围。已有暂存内容保持原状；审查范围还应包括理解改动所需的周边代码、接口和测试。若要 `git commit --amend`，还须审查原 `HEAD` 相对每个父提交的完整差异及本次增量，确认改写历史已获授权；暂存后再次核对拟生成提交相对各父提交的最终差异，不能只看相对旧 `HEAD` 的增量。
2. 派出至少两个相互独立的 subagent，只读审查同一拟提交范围。分别核对需求符合性、逻辑与边界条件、回归风险、测试缺口和安全问题。审查任务中明确禁止编辑文件、暂存、提交和推送；不要把一个代理的结论预先提供给另一个代理。
3. 收齐每个代理的结论，核对其证据。任何可信问题、无法判断的关键风险，或不足两个代理完成独立审查时，先按严重程度向用户列出位置和影响，停止人工暂存、提交及会自动改动暂存区的 Git 操作。只有用户已明确授权处理审查问题时才修复；修改后重新执行完整双代理审查，否则保持现场等待指示。
4. 普通文件改动须在审查和必要的测试、静态检查通过后，才可执行 `git add`、`git mv`、`git rm` 等人工改动暂存区的操作。重命名或删除也可先在工作区完成并审查，再用 `git add -A -- <相关路径>` 暂存；不要对已经移动或删除的旧路径再执行 `git mv`。
5. `merge`、`cherry-pick`、`revert` 即使用 `--no-commit` 也可能自动改动暂存区。先由两个代理审查当前 `HEAD`、操作涉及的提交及将引入或撤销的改动；只有输入审查无问题，才以 `--no-commit` 暂停自动提交。对实际合并或反向应用的最终结果重新完成双代理审查；复审无问题且测试通过后才可人工暂存冲突解决文件并提交。无法暂停自动提交或复审最终结果时，不执行该操作。
6. 人工暂存后检查 `git diff --cached` 与已审查范围一致；自动更新暂存区的操作还要核对完整最终差异。若包含未审查内容或缺少预期改动，停止提交并报告。提交不得使用 `git commit -a`、`--all`、`--include`、`--only`、带路径提交或其他会隐式暂存、改变提交范围的选项。
7. 审查后只要拟提交内容改变，原审查结论即失效，必须重新完成至少两个独立代理的审查；不能沿用旧结论直接暂存或提交。
