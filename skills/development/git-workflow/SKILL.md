# Git 工作流规范

用于确定 Git 操作的顺序和边界。执行前先读取当前仓库的 `AGENTS.md`、相关项目文档和工作区状态；用户明确要求与仓库规则优先于本 Skill 的通用建议。本 Skill 不扩大当前任务对推送、合并、发布或历史改写的授权。

## 开始前

1. 确认仓库、当前分支、远端、目标分支、已暂存和未暂存的改动。已有改动先判断归属，不覆盖、不混入本次任务。
2. 默认在当前 checkout 工作，不创建 Git worktree。仅当用户在当前任务中明确要求使用 worktree 时才创建；其他 Skill 的隔离建议不构成授权。
3. 识别任务是开发、提交、PR、集成测试分支还是发布。目标分支和操作范围不明确时，不自行修改共享分支。

## 新建需求分支

1. 用户未指定来源分支时，实时核实远端默认分支是否为 `main` 或 `master`（例如查询远端 `HEAD` 的符号引用），并确认该远端引用真实存在；不能只信本地缓存的 `origin/HEAD`。如果远端默认分支信息缺失、两个候选主干无法区分，或有其他疑义，先询问用户确定主干名称。不得把当前 checkout 分支当作来源。
2. 即使用户指定来源分支，也不得从 `dev`、`test`、`pre` 等开发或测试分支派生需求分支；发现此类请求时说明冲突并请用户确认 `main` 或 `master`。其他来源分支需有用户明确指示。
3. 创建前 `fetch` 对应远端，比较本地来源分支与远端对应分支的提交。若本地分支不存在，从已核实的远端提交建立同名本地分支；若本地落后且工作区允许，使用 fast-forward 同步。若本地领先、分叉、无法核实或工作区改动可能随切换转移，则停止并说明，不使用 `reset` 或强制覆盖。确认本地与远端来源分支指向同一提交后，从该提交创建新分支。
4. 用户明确给出新分支名称时，先判断需求是新功能 `feat` 还是缺陷修复 `fix`，将名称整理为 `chard/feat-<简短名称>` 或 `chard/fix-<简短名称>`。若原名称表达的类型与需求冲突，先澄清，不擅自改成另一类。未指定名称时也优先使用同一格式；不能判断类型时先确认。

本项目采用功能分支开发、共享测试分支集成的流程。不要把 ECC 示例中的 GitHub Flow、主干开发或 GitFlow 默认分支布局直接套用到当前仓库。

## 提交与审查

- 每个提交只包含一个逻辑变更。先审查工作区差异，再按路径或补丁块暂存，最后检查 `git diff --cached`；不要用 `git add .` 掩盖无关改动。
- 提交前运行与改动相关的测试和静态检查，排除密钥、调试代码、生成产物及无关格式化改动。检查失败应修复或说明阻碍，不能声称已通过。
- 提交消息使用 [上下文提交规范](references/contextual-commits.md)：Conventional Commit 标题与必要的结构化正文，均用中文描述，不编造无法从任务或差异核实的背景。
- PR 聚焦单一需求，说明变更原因、影响范围与验证结果。推送前确认远端、源分支和目标 ref；不得强制推送共享分支。
- 默认在提交后停止，不执行 `git push`、创建或更新 PR，也不推送标签。只有用户明确要求相应操作时才继续；先核对具体远端、源分支、目标分支和范围。

## 合并与冲突

- 通常仅对尚未共享、且没有其他人基于其提交继续工作的功能分支考虑 rebase；已共享分支优先用 merge 保留共同历史。仓库专项流程另有要求时按专项流程执行。未经当前任务明确授权，不得 rebase 或强制推送 `dev`、`test`、`pre` 等共享分支。
- 合并前同步目标分支最新状态，核对源分支相对目标分支的完整差异。共享测试分支按 [共享测试分支集成](references/shared-test-branches.md) 执行。
- 冲突时逐文件检查共同基点、源分支和目标分支的改动，结合需求形成合并结果。不得用整文件 `ours`/`theirs` 或批量放弃一侧改动代替核对。
- 合并后检查冲突标记、实际差异和相关测试及静态检查。失败或需求语义无法判断时停止推送并报告具体问题。
- 生产主干的集成、历史改写、删除远端分支和发布标签均按当前仓库专门规则及用户授权执行；不要从通用示例推断权限。破坏性 `reset` 不能用于处理未知或他人的改动。

## 发布

只有发布任务需要版本号、标签或变更日志。先根据对使用方可见的兼容性变化判断主、次、修订版本，再从已验证的提交创建标签；变更日志应按实际用户影响整理，不直接把 `git log` 当成发布说明。

本规范参考 [ECC 的 git-workflow Skill](https://github.com/affaan-m/ECC/blob/main/skills/git-workflow/SKILL.md)，并按本项目的分支与发布规则调整。
